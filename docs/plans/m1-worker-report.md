## 4. v2 API patterns verified against the installed package (with evidence)

All verification was done by inspecting `backend/node_modules/@medusajs/medusa` (and, where the backend install was initially incomplete, the equivalent `storefront/node_modules/@medusajs/framework` copy at the same version 2.17.2) — not by assuming docs.

### 4.1 `defineConfig` import path (Plan Risk R2)
- `@medusajs/medusa` `dist/index.d.ts` re-exports only `./types`, `./utils`, `./instrumentation`, `./commands`. Its `dist/utils/index.d.ts` re-exports `define-middlewares` etc. but **not** `define-config`. So `defineConfig` is **not** exported from `@medusajs/medusa`.
- `@medusajs/framework` `dist/index.d.ts` (v2.17.2) re-exports `./config`, `./container`, … but **not** `./utils` at the package root — so `import { defineConfig } from "@medusajs/framework"` does **not** resolve in 2.17.2.
- `defineConfig` actually lives in `@medusajs/utils/dist/common/define-config.*` (function `defineConfig(config?: InputConfigWithArrayModules): ConfigModule`). The framework surfaces it via its **subpath export** `"./utils"` (`framework/package.json` `exports["./utils"]` → `dist/utils/index.js`, which does `export * from "@medusajs/utils"`).
- **Decision:** `import { defineConfig } from "@medusajs/framework/utils"` in `medusa-config.ts`. This required `moduleResolution: "Bundler"` (classic `node` resolution does not honour package `exports` subpaths). This subpath is a documented export of the framework package, so it is the cleanest correct option. (Equivalent fallback would be `import { defineConfig } from "@medusajs/utils"`.)
- Evidence: `backend/node_modules/@medusajs/framework/package.json` exports field; `…/framework/dist/utils/index.d.ts` (`export * from "@medusajs/utils"`); `…/framework/node_modules/@medusajs/utils/dist/common/define-config.d.ts`.

### 4.2 v2 module service registration keys (Plan Risk R8)
- Verified the `Modules` enum in `@medusajs/utils/dist/modules-sdk/definition.d.ts`:
  - `Modules.PRODUCT = "product"`, `Modules.REGION = "region"`, `Modules.PRICING = "pricing"`, `Modules.PAYMENT = "payment"`, `Modules.FULFILLMENT = "fulfillment"`, `Modules.SALES_CHANNEL = "sales_channel"`, `Modules.CURRENCY = "currency"`, etc.
- **There is no `PRODUCT_CATEGORY` key in the `Modules` enum.** Product categories are managed by the product module service itself via `createProductCategories` / `listProductCategories` (verified on `@medusajs/product/dist/services/product-module-service.d.ts`, lines 155–163). So the plan's suggested `container.resolve("productCategory")` was **not** used; categories go through the resolved `product` module service. This is an intentional, evidence-based deviation from the plan's "likely" guess.
- Remote link registration key: `ContainerRegistrationKeys.LINK = "link"` (also `REMOTE_LINK = "remoteLink"`, deprecated) — verified in `@medusajs/utils/dist/common/container.d.ts`.

### 4.3 Seed script signature
- Verified `@medusajs/medusa/dist/commands/exec.js`: `medusa exec <file>` builds `scriptParams = { container, args }` and calls `scriptToExec(scriptParams)`. So the seed signature is `export default async function seed({ container })`. (The v1 scripts used `export default async function x(container)` — a single positional arg — which would **not** receive the container under v2. The new seed uses the destructured `{ container }` form.)

### 4.4 `defineMiddlewares`
- Re-exported from `@medusajs/medusa` (`dist/utils/define-middlewares.d.ts` → `@medusajs/framework/http`). `import { defineMiddlewares } from "@medusajs/medusa"` resolves under Bundler resolution. Used with an empty `routes: []` array for M1.

### 4.5 Pricing in paise (Plan Risk R5)
- The seed stores every price in paise: ₹1,299 → `amount: 129900`, ₹1,999 → `199900`, ₹2,499 → `249900`, ₹3,999 → `399900`, ₹1,799 → `179900`. Prices are created via the pricing module (`createPriceSets({ prices: [{ amount, currency_code: "inr" }] })`) and linked to each variant via `remoteLink.create({ [Modules.PRODUCT]: { product_variant_id }, [Modules.PRICING]: { price_set_id } })`.

## 5. Assumptions made

1. **`@medusajs/framework` added as an explicit dependency.** The plan's task-3 keep-list said "Keep @medusajs/medusa, typescript, ts-node, @types/node" and did not list `@medusajs/framework`. However, `@medusajs/framework` is a **required peer dependency** of `@medusajs/medusa@2.17.2` (declared in `@medusajs/medusa/package.json` `peerDependencies`), is imported by every core module (`@medusajs/product`, `@medusajs/region`, …), and is the only clean source of `defineConfig`. Without it the app cannot boot and `tsc` cannot resolve framework imports. The prior backend `node_modules` was missing it entirely (the install was incomplete). Adding it is required infrastructure, not scope-widening. Pinned to `2.17.2` to match `@medusajs/medusa`.
2. **`module: "ES2022"` + `moduleResolution: "Bundler"`** chosen for `tsconfig.json` to match Medusa v2 conventions and to support package `exports` subpaths (`@medusajs/framework/utils`). `medusa-config.ts` uses `module.exports = defineConfig(...)` (CommonJS) which is **not** type-checked by `tsc` (it lives at the backend root, outside `include: ["src/**/*"]`) and is transpiled at runtime by Medusa's config loader — consistent with the draft-order README pattern.
3. **`DOM`/`DOM.Iterable`** added to `lib` because the admin stubs use browser APIs (`document`, `confirm`, `EventTarget.value`, `HTMLImageElement.style`, `Response.json()`). Without DOM lib these produced ~40 errors.
4. **`@medusajs/admin-sdk` ambient stub.** The dashboard widget stub imports `defineWidgetConfig` from `@medusajs/admin-sdk`, which is not installed as a standalone package (it is provided by `@medusajs/admin-bundler` at build time). A permissive ambient module declaration (`src/admin/admin-sdk.d.ts`) makes the stub compile without building real admin features, per task 8.
5. **Loose typing on resolved services in `seed.ts`.** The resolved module services are typed pragmatically (locals treated as `any` for method calls) to guarantee compilation given the large/uncertain DTO surface and the incomplete `@medusajs/types` `.d.ts` shipping in some copies. The v2 logic (service keys, method names, paise, link keys) is verified-correct; tightening types is low-risk M2 polish.
6. **Manual/COD payment provider not wired in the seed.** The plan asked to "include manual/COD payment provider setup", but no v2 manual payment provider package is installed (only `@medusajs/payment` and `@medusajs/payment-stripe` are present; the v1 `medusa-payment-manual` was removed). `defineConfig`'s defaults already register the manual fulfillment provider and the stripe payment provider. A v2 COD/manual payment provider is **M2/M4 scope** (plan Risk R7) and requires either a community v2 provider or a custom provider module. The seed does not register a non-existent provider to avoid runtime errors; this is noted rather than silently faked.

## 6. Blockers / things that will matter once Docker is available

- **Docker is off** (per constraints), so none of the runtime verification was attempted: `medusa db:migrate`, `medusa exec src/scripts/seed.ts`, `medusa develop`, and `curl http://localhost:9000/store/products` are **pending** and must be run once Postgres+Redis are up (`docker-compose up -d postgres redis`). These are the gated M1 runtime checks.
- **`backend/.env` does not exist** (gitignored). It is referenced by `medusa-config.ts` via `process.env`. Create it before booting:
  ```
  DATABASE_URL=postgres://myntra:myntra_pass@localhost:5432/myntra_store
  REDIS_URL=redis://localhost:6379
  JWT_SECRET=<secret>
  COOKIE_SECRET=<secret>
  STORE_CORS=http://localhost:3000
  ADMIN_CORS=http://localhost:9000
  AUTH_CORS=http://localhost:9000
  ```
  (The explicit task list for this run did not include `.env` creation, so it was left to the operator.)
- **Admin user** must be created manually with `npx medusa user -e admin@myntra-clone.com -p <password>` before logging in to the native admin at `http://localhost:9000/app`.
- **Seed idempotency:** region and products are guarded against re-creation (checks by name/handle). Categories are guarded by handle. Re-running `npm run seed` is safe.
- **Pricing↔variant link shape:** the seed links price sets to variants using `{ [Modules.PRODUCT]: { product_variant_id }, [Modules.PRICING]: { price_set_id } }`. This is the standard v2 link shape but should be confirmed at first runtime; if the link module key names differ, `/store/products` prices may come back empty and the link keys would need adjustment (M2).
- **Admin stubs are stubs.** `src/admin/routes/*.tsx` still call v1-style endpoints (`/admin/products?page=…`, `/admin/analytics/dashboard`, etc.) and the `index.tsx` is a standalone SPA-style page rather than a true v2 admin route module. They compile but are **not functional v2 admin extensions** and will not be served correctly by the v2 admin-bundler as-is. Proper v2 admin route/widget authoring is beyond M1 (the plan keeps these as stubs); M2 task 10 covers aligning admin widgets with the native v2 admin API.
